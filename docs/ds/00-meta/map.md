# FP-DS-2026 — module map

The design system is split into modular docs so an agent (or a person) loads only
what a task needs. **Load this file first**, then pull the relevant module(s).

## Structure

Three design categories, each with the **same six facets**, plus a meta spine.

| Category | Covers | Filing rule |
|---|---|---|
| **`ux/`** | structure, flow, information, spatial grouping | *"where things go / how they're organized"* |
| **`ui/`** | visual surface: tokens, color, type, surfaces, component looks | *"how it looks"* |
| **`interactions/`** | behaviour, state, feedback, motion, accessibility | *"how it behaves"* |

Each category folder holds the six facet files, **in this order**:

1. `1-fundamentals.md` — principles & the mental model (the *why*)
2. `2-rules.md` — **canonical** normative rules (the *what*) — the single source
3. `3-dos-and-donts.md` — quick one-line pointers into the rules
4. `4-common-mistakes.md` — ❌/✅ anti-patterns pointing back to the rules
5. `5-checks.md` — verifiable assertions derived from the rules
6. `6-execute.md` — how to build it (code, recipes, inventory)

> **Rules are canonical.** The normative statement lives once, in `2-rules.md`.
> The other facets reference it — they never restate the full rule.

## Applications built on this DS

An application that adopts the DS keeps its OWN doc set, as a child. It records
how it uses the system and what it has bound meaning to; it never redefines a
component, and anything general it settles is promoted UP into these rules.

| App | Docs |
|---|---|
| Unified View | `docs/unified-view/map.md` |

**When a child doc and these rules disagree, these rules win** and the child is
out of date. Its `evals/` exist to catch that.

## The meta spine (`00-meta/`)

| File | For |
|---|---|
| `map.md` | this router |
| `constitution.md` | the locked, non-negotiable rules (load with any build) |
| `setup.md` | adopting the DS in a new prototype (stack · tokens · theme) |
| `prompt-preamble.md` | copy-paste preamble for an AI coding tool |
| `conformance.md` | the ship-gate checklist (rolls up every category's `5-checks`) |
| `workflow.md` | building/extending the DS itself (Figma→React loop, packaging) |

## Which file for what

| Task | Pull |
|---|---|
| Restyle a prototype onto the DS | `constitution` + `setup` + `ui/*` + `ux/2-rules` + `interactions/2-rules`, then `conformance` |
| Lay out a screen / header / zones | `ux/*` |
| Pick colors, tokens, surfaces, type | `ui/1,2,6` |
| Choose a component / pattern | `ui/6-execute` + `ux/3-dos-and-donts` + `08` in-app Do's & Don'ts |
| Add behaviour, focus, feedback, charts | `interactions/*` |
| Extend the DS from a Figma frame | `00-meta/workflow` + `constitution` |
| Ship-check | `00-meta/conformance` |

## Cross-cutting principles (stated per category, canonical once)

- **Emphasis budget / one primary action** — canonical: `ux/2-rules` (H3). UI states the CTA-neutral facet; Interactions references it.
- **Elevation steps once (H2)** — canonical: `ux/2-rules`; cross-refs `ui` surfaces.
- **Theme toggle** — concept: `ui/1-fundamentals`; wiring: `00-meta/setup`.

## Generated bundle

`docs/apply-design-system.md` is an **auto-concatenated bundle** of `ui + ux +
interactions` (+ setup & preamble) for the "hand an agent one file" flow. It is
generated by `docs/ds/build-bundle.sh` — **do not hand-edit it**; edit the modules
and regenerate.
